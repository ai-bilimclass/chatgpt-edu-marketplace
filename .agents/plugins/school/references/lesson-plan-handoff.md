# ҚМЖ/КСП handoff для производных материалов

Рабочий, практический или лабораторный лист и новая презентация создаются только на основе готового ҚМЖ/КСП/Lesson Plan.

Допустимы два источника:

1. прикреплённый учителем файл плана урока в читаемом формате;
2. последняя успешно созданная и проверенная плагином версия плана урока в текущем чате, автоматически переданная как `lesson_plan_handoff`.

Само наличие темы, цели, КТП или краткого описания урока не заменяет готовый план. План из другого чата повторно не восстанавливать по памяти: попросить прикрепить файл.

## Контракт handoff

Сразу после успешного создания, проверки и передачи плана урока автоматически сохранить внутренний пакет, не требуя фразы `ҚМЖ-ны қабылдаймын`, `КСП принимаю`, `I accept the lesson plan` или иного отдельного подтверждения:

```yaml
lesson_plan_handoff:
  schema_version: "3.0"
  lesson_content_version: "lesson-<stable-id>-v1"
  source: "same_chat_generated_lesson_plan"
  ready_for_derivatives: true
  continuity_notice_shown: false
  artifact_path: ""
  grade: ""
  subject: ""
  instruction_language: ""
  document_language: ""
  topic: ""
  duration_minutes: 40
  learning_objectives: []
  assessment_criteria: []
  lesson_stages: []
  required_tasks: []
  expected_answers: []
  formative_assessment: []
  support_and_extension: []
  homework: ""
  sources: []
  content_boundaries:
    previously_learned: []
    introduced_in_this_lesson: []
    deferred_content: []
    prohibited_assumptions: []
    allowed_example_types: []
    unknowns: []
    source_refs: []
  episodes: []
  canonical_tasks: []
  canonical_answers: []
  source_bindings: []
  math_objects: []
  validation_status: "strict"
  unresolved_limitations: []
  derivative_registry:
    worksheets: []

  methodology:

    specialized_method: ""

    learning_evidence: []
    formative_decision_points: []
    next_teacher_actions: []
    differentiation_and_accessibility: []
```

## Версионирование содержания

`schema_version: "3.0"` обозначает строгий контракт. `lesson_content_version` — стабильный идентификатор конкретной содержательной версии плана, а не номер версии плагина. Увеличивать суффикс `v1`, `v2`, `v3` после любого изменения, которое влияет на точную цель, границы содержания, последовательность эпизодов, инструкции, задания, ответы, доказательства, критерии, поддержку или формативное решение. Изменение только визуального оформления без изменения смысла не создаёт новую содержательную версию.

Новый или существенно изменённый план всегда формировать по версии 3. Пакет версии 2.0 разрешено только читать в режиме обратной совместимости с `validation_status: legacy_unverified`: он не проходит строгую синхронизацию, пока задания и методы не преобразованы в структуру версии 3. Старый пакет без `schema_version`, `lesson_content_version` и расширенных блоков допустим только как контракт версии 1 и также не даёт права утверждать, что производные материалы синхронизированы на уровне эпизодов.

В версии 3 каждый этап содержит `activity_type`, массив `methods`, обычные `teacher_actions`, массив `tasks` и `resources`. Каждый метод имеет уникальные `method_id`, `type: primary | supporting | technique` и чистое `name` без Markdown-разметки и локализованного префикса. Каждое учебное задание содержит уникальный `canonical_task_id`, `task_type`, `objective_refs`, `instruction`, `learner_action`, `expected_product`, отдельный наблюдаемый `descriptor` и `feedback`. Организационный этап может не иметь заданий; учебный этап обязан иметь хотя бы одно.

## Канонические эпизоды и задания

Каждый элемент `episodes` соответствует [контракту практического учебного эпизода](../skills/school-lesson-planner/references/practical-episode-contract.md) и имеет уникальный `episode_id`. Не менять идентификатор, пока сохраняется учебная функция эпизода. Существенно другой эпизод получает новый идентификатор.

`canonical_tasks` хранит только задания, которые должны одинаково воспроизводиться в связанных материалах:

```yaml
canonical_tasks:
  - canonical_task_id: "task-01"
    episode_id: "episode-01"
    instruction: ""
    student_input: ""
    expected_product: ""
    descriptor: ""
    assessment_criteria_refs: []
```

Поле `descriptor` обязательно и непусто для каждого `canonical_task_id`. Каждое отдельное учебное задание получает собственный локализованный наблюдаемый дескриптор; один общий дескриптор нельзя применять к нескольким заданиям. Рабочий лист и презентация сохраняют этот дескриптор при переносе задания.

`canonical_answers` связывает проверяемый ответ с заданием:

```yaml
canonical_answers:
  - canonical_answer_id: "answer-01"
    canonical_task_id: "task-01"
    expected_answer: ""
    acceptable_variations: []
    likely_misconceptions: []
```

В `source_bindings` для каждого существенного элемента хранить `source_ref`, тип источника и при наличии страницу, лист, диапазон или раздел. Не добавлять фиктивную привязку, если источник неизвестен: поместить ограничение в `unresolved_limitations`.

Если практический приём найден через гибридный поиск, добавить в `source_bindings` обязательный блок с полями `source_type: external`, `source_url`, `source_title`, `source_organization`, `checked_at`, `source_status` и `adaptation_note`. `source_status` принимает только `verified` или `usable_with_limits`; `checked_at` — фактическую дату проверки. Не сохранять отклонённого кандидата как применённый источник. В `episodes[].technique_id` использовать стабильный локальный `candidate_id`, не маскируя внешний приём под ID встроенного каталога. Гибридный поиск не применяется к КТП, учебникам, учебным программам и целям обучения.

Если план содержит формулы, заполнить `math_objects` по [контракту редактируемых математических объектов](editable-math-contract.md). Сохранять `math_id`, канонический Presentation MathML, проверочную запись LaTeX, локализованное чтение, переменные, единицы и источник. Рабочий лист, оценочный материал и презентация используют тот же `math_id`; изменение математического смысла увеличивает `lesson_content_version` и переводит старые производные материалы в `requires_regeneration`.

## Связь с рабочими листами и презентациями

После создания производного материала зарегистрировать его в `derivative_registry`:

```yaml
derivative_registry:
  worksheets:
    - artifact_id: "worksheet-01"
      source_lesson_content_version: "lesson-<stable-id>-v1"
      status: "current"
      mappings:
        - episode_id: "episode-01"
          canonical_task_id: "task-01"
          worksheet_task_id: "worksheet-task-01"
          descriptor: ""
  presentations:
    - artifact_id: "presentation-01"
      source_lesson_content_version: "lesson-<stable-id>-v1"
      status: "current"
      mappings:
        - episode_id: "episode-01"
          canonical_task_id: "task-01"
          slide_id: "slide-05"
          descriptor: ""
```

Связь `episode_id → worksheet_task_id` или `episode_id → slide_id` должна прослеживаться для каждого перенесённого ключевого эпизода. В каждой связи сохранять точный `descriptor` исходного `canonical_task_id`. Перед выдачей рабочего листа или презентации сформировать машинно-проверяемый манифест с `artifact_type`, `source_lesson_content_version` и `items[]`, затем выполнить `scripts/validate_derivative_alignment.py`. Результат `PASS` обязателен; неизвестный или пропущенный ID, старая версия содержания и изменение дескриптора блокируют выдачу. Несколько слайдов могут поддерживать один эпизод, но они не должны создавать противоречащую инструкцию или ответ. Рабочий лист может включать дополнительное тренировочное задание, если оно не меняет цель и явно имеет новый локальный ID; не выдавать его за каноническое задание плана.

Если `lesson_content_version` изменился, все ранее зарегистрированные рабочие листы и презентации на старой версии автоматически получают `status: "requires_regeneration"`. Не называть их синхронизированными и не продолжать молча по старому содержанию. Сообщить учителю, какой материал устарел, и предложить пересоздать его; не изменять ранее выданный файл без запроса.

`ready_for_derivatives: true` устанавливать только после успешного завершения содержательной, структурной и визуальной проверки и передачи готового файла учителю. Не устанавливать для черновика, ошибки, незавершённой генерации или файла, не прошедшего обязательную проверку. Это состояние означает готовность использовать текущую версию как основу производных материалов, а не формальное утверждение документа учителем или школой.

Производный навык принимает пакет без повторной загрузки файла и без подтверждающей фразы, если он относится к текущему чату, полный для запрошенного продукта и не существует более новой или противоречащей версии плана. Если учитель изменил план или указал использовать другой документ, обновить пакет по новой версии. В другом чате попросить прикрепить файл.

Если в текущем чате есть несколько готовых планов разных классов, предметов или тем и выбор основы неоднозначен, до разработки задать один короткий вопрос, какой именно план использовать. Не выбирать план только по давности, если новый запрос может относиться к другому классу или предмету.

После приёма пакета не спрашивать повторно класс, предмет, язык обучения, тему, продолжительность и точные цели. Язык обучения автоматически считать языком производного документа, если учитель прямо не указал другой язык результата. Одним сообщением запросить только параметры, специфичные для нового материала.

Блок `methodology` формирует только `school-lesson-planner` по [центральному методическому маршрутизатору](../skills/school-lesson-planner/references/methodology-router.md). Производный навык применяет подтверждённое решение и не выбирает другую основную методику. Пустой `supporting_method` или `specialized_method` допустим. Если прикреплённый план не содержит явной методической модели, производный навык не должен придумывать её: использовать только зафиксированные этапы, задания, критерии и доказательства.

Для контракта версии 2 производный навык также не выбирает заново `thinking_process`, `technique_id` или `interaction_id`: он переносит их из соответствующего эпизода и адаптирует только форму представления. При конфликте между общим текстом и каноническим заданием остановить сборку производного материала, зафиксировать `LIMITATION` и запросить решение учителя либо обновление плана.

## Одноразовое уведомление о продолжении работы в одном чате

После каждого успешно созданного ҚМЖ/КСП/Lesson Plan вывести одну рекомендацию на языке текущего запроса. Рекомендация носит информационный характер: оформить её жирным курсивом, не просить согласия, подтверждения или специальной фразы и не показывать три языковые версии одновременно. Не акцентировать внимание на новом чате или повторном прикреплении файла.

- қазақша: ***Бір сынып пен бір пәнге арналған сабақ материалдарын бір чатта құрастырып, жалғастырған ыңғайлы. Сондықтан оқу материалдарын осы чатта жалғастыруды ұсынамыз.***
- русский: ***Материалы уроков для одного класса и одного предмета удобно создавать и продолжать в одном чате. Поэтому рекомендуем продолжить работу над учебными материалами в этом чате.***
- English: ***It is convenient to create and continue developing lesson materials for the same class and subject in one chat. Therefore, we recommend continuing the work on these learning materials in this chat.***

Перед созданием каждого производного материала в текущем чате вывести только короткое локализованное примечание: `Материал будет подготовлен на основе последнего ҚМЖ/КСП в этом чате` либо его казахский или английский эквивалент. Если учитель указал другой план, назвать выбранный план вместо последнего. Не утверждать, что план сохранён в постоянной памяти.

После рекомендации при необходимости показать приглашение к опросу, а затем обязательно показать обычный выбор следующего материала. Рекомендация не является вопросом и не блокирует дальнейшую работу.

## Перенос баллов дескрипторов

Для КСП и рабочих листов применять [контракт дескрипторов с баллами](scored-descriptors.md). В каноническом задании сохранять `descriptor_scores` (массив `text`, `points`), `total_points` и при наличии `support`; вместе с этапом сохранять `work_forms`. Переносить эти значения в рабочий лист без изменения. Если баллы дополняют старый план, обновлять версию содержания исходного КСП и handoff до проверки производного материала.

`handoff_from_ksp` сохраняет язык, класс, баллы и поддержку; отсутствие баллов блокирует strict-handoff. `validate_alignment` для `worksheet` проверяет каждый текст и балл, общую сумму и поддержку, включая пропущенные поля. Для презентаций сохранён прежний контракт без требования показывать баллы.
